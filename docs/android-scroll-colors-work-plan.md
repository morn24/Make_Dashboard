# 위젯 높이 확장·영역별 스크롤·일정 색상 복구 업무계획서

작성일: 2026-11-01 (KST) · 실제 구현: 새 **Luna (`gpt-6-luna`) / max** 세션

## 1. 범위와 기존 결과 검수

이번 세션은 계획·기존 결과 검수만 수행한다. 사용자가 승인한 구현 요구는 다음 네 가지이며, 개발은 [수행지시문 05](instructions/05-android-scroll-colors-luna.md)를 받은 새 세션에서 진행한다.

| ID | 요구 | 완료 조건 |
|---|---|---|
| S1 | 위젯을 세로로 늘리면 여러 항목이 기본 표시 | 같은 폭·같은 글꼴에서 높이를 늘릴수록 처음 보이는 일정/프로젝트/할 일이 증가 |
| S2 | 각 영역 안에서 위아래 드래그로 다른 항목 확인 | 위젯 안의 실제 네이티브 세로 스크롤로 목록 마지막 항목까지 접근. 웹앱 필수 아님 |
| S3 | 실제 Google 캘린더 색상이 기본값으로만 나오는 문제 | 수집→GitHub color→Android 캐시/mapper→원형 마커 중 실패 지점을 판별하고 수정·검증 |
| S4 | 붉은색·주황색·노란색 강조 조합 추가 | 기존 4종 유지 + 각 계열을 주 강조색으로 하는 새 조합 3종 이상, 밝음/다크/미리보기 일치 |

### 확인한 회귀와 미검증 사항

- 현재 `WidgetLayoutPlanner`는 큰 크기에서도 todoRows=1, projectRows=1로 고정한다. 큰 글씨나 undo가 있으면 일정도 1개로 줄인다. 실제 높이를 연속적으로 사용하지 않는다.
- `WidgetContent`는 목록을 `.take(plan.*Rows)`로 먼저 잘라 패널에 전달한다. 잘린 항목은 위젯 목록에 존재하지 않으므로 스크롤을 추가하는 것만으로 해결되지 않는다.
- `TodoPanel`, `SchedulePanel`, `ProjectPanel`은 `Column + forEach`이며 네이티브 스크롤 목록이 아니다. `sectionPanelModifier`는 패널 전체를 웹앱 클릭으로 지정한다.
- 오른쪽 프로젝트와 왼쪽 컨테이너는 폭 weight만 적용돼 높이를 충분히 사용하지 않을 수 있고, 할 일에는 78dp 고정 높이 분기도 있다. 이전 `widget-4x4-final.png`를 직접 열어 프로젝트 1개/더보기 아래 큰 빈 공간을 확인했다.
- `WidgetLayoutPlannerTest`는 큰 크기의 1개 제한까지 정답으로 고정한다. 이 테스트를 유지한 채 문제를 고쳤다고 판단하면 안 된다.
- 일정 색상 resolver/원형 점 코드는 존재하지만 이전 검증은 익명 RGB fixture였다. 검증 기록에는 **개인 Apps Script에 수정 Code.gs를 아직 적용하지 않음**이 명시되어 있다. 현재 개인 일정의 원격 color 값은 이 계획 세션에서 읽거나 확인하지 않았다.
- Apps Script는 REST 오류를 잡아 캘린더 기본색으로 내려가며, 로그에는 종류만 남겨 HTTP 원인을 구분하기 어렵다. `eventLabelVersion=1`을 항상 쓰는 경로와 fields/라벨/팔레트 실패를 별도로 검증해야 한다. 어느 하나가 실제 원인이라고 아직 단정하지 않는다.
- palette resolver는 고정 legacyAccent에 새 팔레트를 낮은 비율로 섞어, 따뜻한 색을 추가해도 녹색 계열이 강하게 남을 수 있다. 새 조합의 주 강조색이 실제 화면에서도 해당 계열인지 검수한다.

## 2. 이번 지시가 우선하는 부분

공유 JSON 형식·기존 계정/설정·2단 패널·빠른 체크·undo·다크/투명도는 유지한다. 다만 초기 02~04의 '최대 3개 할 일/5개 일정/4개 프로젝트만 제공', '다중 스크롤 대신 더보기 허용'은 **이번 사용자 지시로 대체**한다. 그 숫자는 기본 가시량 설계 참고일 뿐이며 로드할 목록의 잘라내기 상한으로 쓰지 않는다.

`SizeMode.Exact`는 직전 구현에서 삼성 런처 실제 크기를 받기 위해 채택한 상태이므로 유지하고, 이유 없이 Responsive로 되돌리지 않는다. 사용자에게 중요한 것은 실제 높이 반영·2단·스크롤이다.

## 3. S1: 높이에 따른 실제 가시량

### 데이터와 뷰포트 분리

- 패널에는 필터/정렬만 적용한 **전체 목록**을 전달한다: 표시 대상 할 일 전체(보류 행 포함), 오늘 일정 전체, active 프로젝트 전체. `.take(1)`, `.take(4)` 등으로 스크롤 데이터 자체를 잘라내지 않는다.
- planner는 columns·panel height·행 높이/가시량 예산을 계산한다. 가시량은 `floor((패널 높이 - 제목/여백)/예상 행 높이)` 등으로 추정할 수 있지만 실제 목록 크기 제한으로 사용하지 않는다.
- 전체 높이에서 헤더·요약·상태·undo·여백의 실제 공간을 제외하고 본문에 **유한한 높이**를 배정한다. 본문과 좌우 컬럼에 높이 채우기를 명시해 wrap-content 때문에 빈 공간을 남기지 않는다.
- 큰 위젯은 왼쪽 할 일/오늘 일정, 오른쪽 프로젝트의 2단을 유지한다. 오른쪽은 본문 높이 전체를 사용한다. 왼쪽 두 패널은 공간을 나누되 빈 영역은 접거나 재분배한다. 할 일/일정 중 한 영역에 더 많은 내용이 있으면 남는 공간을 합리적으로 사용한다.
- 78dp 할 일 고정 높이와 undo 발생 시 목록을 한 개로 잘라내는 분기를 제거한다. undo는 헤더/별도 공간을 차지할 뿐 데이터 손실이나 스크롤 제거의 이유가 아니다.
- 폭이 좁은 세로 위젯도 높이가 늘면 표시량이 증가한다. 작은 2×2는 간략 요약이 가능하나, 일정/프로젝트를 상세 영역으로 제공하는 크기에서는 1개로 영구 제한하지 않는다.
- 글씨 크기와 시스템 배율을 반영해 행의 최소 높이·줄바꿈을 정한다. 48dp 체크 터치 영역을 줄이거나 폰트를 축소해서 개수를 늘리지 않는다.

### 수치 검수

같은 데이터·폭·글꼴에서 높이 약 300/490/650dp 등 실제 지원되는 세 구간을 비교한다. 높이를 한 행 이상 늘릴 때 가시량이 늘고, 긴 위젯에서 적어도 여러 일정과 여러 프로젝트가 스크롤 없이 처음부터 보여야 한다. 기본 100%·폭 260dp 이상·높이 490dp 이상인 대표 fixture에서는 일정 2개 이상과 프로젝트 2개 이상을 출발 목표로 삼고 실제 글꼴/런처에서 검증한다. 더 긴 높이에서는 더 많이 보여야 한다. 공간이 충분한데도 1개면 실패다.

## 4. S2: 패널별 네이티브 스크롤

### 필수 구조

- 각 큰 패널은 `Column(유한 높이)` 안에 작은 고정 제목/전체 개수와 **남은 높이를 채우는 Glance LazyColumn**을 둔다. 모든 항목을 `items`로 등록하고 id를 widget/section/item에 맞게 안정적으로 부여한다.
- 2단 본문 바깥을 다시 세로 LazyColumn/ScrollView로 감싸지 않는다. 같은 방향의 중첩 collection 대신 할 일·일정·프로젝트의 **나란한/분리된** 목록을 사용한다.
- 작은 폭에서 패널별 목록을 배치하는 경우도 각 목록에 명시적 높이를 준다. 2×2의 요약형은 유한한 단일 본문 목록으로 전체 요약/접근을 제공할 수 있으나, 큰 크기에서 전체를 단일 스크롤로 바꾸어 영역별 스크롤 요구를 대신하지 않는다.
- **rootModifier와 sectionPanelModifier를 포함해 패널/스크롤 영역 전체의 `clickable(webAction)`를 제거**한다. 웹앱 이동은 제목의 별도 명시적 버튼·관리 헤더의 '웹앱 열기'처럼 목적이 분명한 액션에만 남긴다. 목록의 빈 곳 터치가 자동으로 브라우저를 열면 실패다. 체크/undo는 독립 액션을 유지한다.
- '+N개 더보기'로 나머지를 접어 웹앱으로 보내는 동작을 기본 탐색 방식으로 사용하지 않는다. 전체 개수·스크롤 가능함을 짧게 표시할 수 있다. 웹앱은 추가/수정 같은 별도 목적의 선택 경로다.

### 제스처·상태

- 사용자 요구의 '드래그'는 **짧게 터치한 뒤 위아래로 움직이는 세로 스와이프**다. 길게 누른 뒤 위젯을 옮기는 런처 편집 동작이나 항목 순서 변경을 구현하는 것이 아니다. 별도 pointer 드래그 구현 대신 플랫폼 collection의 스크롤을 사용한다.
- 일정에서 스와이프하면 일정만, 프로젝트에서 스와이프하면 프로젝트만 이동한다. 스크롤 시작으로 체크가 토글되거나 브라우저가 열리지 않아야 한다.
- stable item id를 사용하고 재렌더마다 목록 view를 불필요하게 새로 만들지 않는다. 네트워크 상태나 다른 todo의 pending 변경 때 타 영역이 맨 위로 튀는지 실제 확인한다. 공개 API로 보장할 수 없는 위치 복원은 한계를 기록한다.
- Glance의 다중 collection을 먼저 실제 런처에서 검증한다. 플랫폼 문제가 있으면 공식 `AndroidRemoteViews`/RemoteViews collection 연동을 패널 수준에 한해 검토할 수 있다. 이것은 로컬 Android UI 구현 대안이며 외부 서비스 도입이 아니다. widget id/section별 adapter id와 데이터 식별자를 분리한다.
- **웹앱/목록 자르기로 후퇴하는 대안은 승인하지 않는다.** 기술 대안을 검증한 뒤에도 실제 스크롤을 만들지 못했으면 S2는 미완료로 남기고 정확한 원인을 보고한다.

## 5. S3: 실제 색상 문제의 단계별 진단·수정

### 증거부터 구분

다음 경로의 첫 손실 지점을 판별한다. 실제 접근 권한이 없으면 개인 데이터를 추측하지 않고 각 단계의 익명 통합 검증과 필요한 사용자 조치를 남긴다.

```text
Google의 캘린더/개별 일정/라벨 색
 → 설치된 Apps Script 버전·권한·REST 응답
 → GitHub calendar.json의 실제 color HEX
 → Android 캐시·CalendarEvent.color
 → 위젯 원형 마커 중심 RGB
```

- 설치된 스크립트가 이전 버전인지, Calendar API 미활성/권한 오류인지, 정상 응답에서 라벨/팔레트/회차 결합이 누락되는지, 원격 color는 맞는데 앱에서 중립색으로 바뀌는지를 각각 분리한다.
- 실제 파일을 읽을 수 있는 승인된 연결이 있으면 확인하되, 출력에는 제목·메일·토큰·원본 JSON을 노출하지 않는다. valid color 수/서로 다른 색 수/정규화 후 HEX 샘플 등 필요한 최소 진단만 사용한다. 같은 색이 많다는 사실만으로 오류라고 단정하지 않는다.
- 기존 Apps Script 프로젝트에 접근할 수 있으면 대상 프로젝트부터 확인해 실제 적용 상태를 검수한다. 인증/새 권한 승인 화면은 사용자 동작으로 남긴다. 임의의 다른 프로젝트에 코드를 붙여넣지 않는다. 접근 불가면 저장소 코드·테스트·APK·정확한 적용 절차를 먼저 완성하고 실서비스 검증은 미완료로 구분한다.

### 코드 수정 기준

- 색상 우선순위는 기존대로 **유효한 개별 라벨/일정 색 → 해당 캘린더의 실제 HEX → 안전한 중립색**이다. Google 캘린더 기본색이 정당한 경우는 유지하고 앱 기본 강조색으로 대체하지 않는다.
- `CalendarEvent.getColor`의 ID와 HEX를 구분한다. REST의 label 경로와 legacy colorId 경로는 별개로 검증한다. labelVersion/fields 미지원 400, 권한 401/403, 요청 제한 429, 5xx에 대해 안전하게 호환 경로를 선택하고 실패 원인을 숨기지 않는다.
- 팔레트 API가 실패해도 정상 캐시가 있으면 사용한다. 캐시 없는 첫 실행의 legacy ID까지 모두 중립색이 되지 않도록 공식 근거가 있는 매핑/호환 경로를 검토한다. 임의 추측한 색상표나 사용자 계정과 무관한 fixture 색으로 '실제 Google 색상 복구'라고 보고하지 않는다.
- calendar label 읽기 실패가 legacy 경로 전체를 막지 않게 한다. 페이지 중간 실패나 반복/이동/종일/다른 시간대 회차 매칭 실패를 진단한다. 데이터 본문은 보존하고 색상 출처별 fallback 수를 집계한다.
- `refreshCalendarColors`는 실행 메모리/영속 캐시를 실제 우회하고 색만 바뀌어도 GitHub를 갱신해야 한다. 트리거 event 객체를 강제 새로고침 boolean으로 오인하지 않게 진입점 인자를 명확히 한다.
- `diagnoseCalendarColors` 같은 읽기 중심 진단 함수를 제공한다. 수집기 버전, API 단계·HTTP 오류 종류, 원격 color 유효 개수, label/legacy/calendar/fallback별 개수를 안전하게 출력한다. 기존 공유 JSON에 필수 진단 필드를 추가하지 않는다. 색상 검증을 위해 Google 일정을 만들거나 바꾸지 않는다.
- Android는 유효한 `#RRGGBB`를 원형 마커에 그대로 전달하고 테마/투명도/프리셋으로 RGB를 바꾸지 않는다. 기존 cache SHA/갱신 규칙과 색만 바뀐 응답 반영도 확인한다.

### 검수 구분

가짜 빨강/파랑/초록 JSON을 넣은 화면은 **렌더 검증**이고 개인 Google 일정 수집 검증이 아니다. 이전 검증이 이 구분을 충족하지 못한 부분을 반복하지 않는다. 실제 upstream→JSON→화면 일치는 가능한 경우 읽기 확인으로 증명하고, 불가능하면 어떤 단계가 미확인인지 분명히 기록한다.

## 6. S4: 따뜻한 강조 조합 3종 추가

|---|---|---|---|
| 코랄 레드 · 세이지 · 크림 | `#F49A91` | `#A4D5C1` | `#F2D8A5` |
| 살구 오렌지 · 블루 · 민트 | `#FFBC80` | `#ADC9F2` | `#B5DDC6` |
| 버터 옐로 · 스카이 · 플럼 | `#F5DE7B` | `#A4CEE9` | `#D7B8DE` |

- HEX는 어두운 화면의 디자인 출발점이다. 밝은 바탕에서는 동등한 계열의 어두운 전경색과 은은한 패널색을 해석해 대비를 확보한다. 대비 계산과 실제 미리보기로 조정한다.
- 새 따뜻한 팔레트의 주요 액션/진행률은 해당 계열이 실제로 주도해야 한다. 기존 녹색 legacyAccent에 22~45%만 섞어 결국 초록처럼 보이게 만들지 않는다. 사용자 지정 HEX 모드와 프리셋 해석은 명확히 구분한다.
- 색상 역할은 기존 공통 resolver로 해석하고 Glance/Compose/추가 미리보기가 같은 값을 사용한다. calendar 원형 점은 독립적으로 유지한다.
- 오류는 아이콘·문구와 별도 오류색으로 구분한다. 빨간 프리셋을 선택했다고 정상 상태가 오류처럼 보이면 조정한다.
- 선택 견본, 개별/전체 적용, draft 취소/기본값, 재시작 저장, 다크 바탕·투명도 유지까지 검증한다. 기존 팔레트 id를 변경하거나 모든 위젯에 새 조합을 강제로 적용하지 않는다.

## 7. 구현 단계와 실패를 걸러낼 검수

| 단계 | 산출물 | 반드시 통과할 증거 |
|---|---|---|
| A | 전체 데이터/높이 예산·실제 공간 채우기 | 목록 20개가 잘리지 않는 표시 모델, 동일 폭 높이 증가에 가시량 증가, 1개 고정 테스트 교체 |
| B | 영역별 실제 네이티브 collection | 세 영역에서 마지막 항목까지 위젯 내 스와이프, 브라우저 미실행, 다른 영역 독립 유지 |
| C | 색상 진단·호환 수정·캐시 갱신·적용 절차 | API 성공/미지원/권한/첫 실행 실패·부분 페이지 fixture, 수집→JSON→mapper→원형 RGB 연계 |
| D | 따뜻한 3종과 호환 저장 | 기존4+신규3 선택 가능, 실제 red/orange/yellow 계열 차이, 대비·테마·원형 색 보존 |
| E | 통합 렌더/제스처 검증·업데이트 APK·문서 | 아래 실험과 실제 Gradle/Node 결과, 전후 화면·스크롤 후 화면·측정·대응표 |
| F | S25 및 실제 Google 원색 최종 확인 | 사용자 확인 전 미완료 |

### 실제 장치/에뮬레이터 검증

1. **20/20/20 fixture:** 할 일 20개, 오늘 일정 20개, active 프로젝트 20개를 서로 구별되는 제목과 stable id로 준비한다. 처음/중간/마지막 항목을 안드로이드 위젯에서 확인한다. 각 목록의 20번째가 실제로 나타나야 한다. 숨김 수가 줄거나 웹앱이 열린 것으로 대체하지 않는다.
2. **제스처 증거:** 일정 패널 위쪽→아래쪽으로 두 방향 스와이프, 프로젝트 패널도 같은 검증, 할 일 체크 행에서 시작한 스와이프를 실제 입력한다. 스크롤 전/후 캡처와 보이는 항목 id/목록 bounds를 기록하고 다른 패널이 움직이지 않았는지 확인한다. 항목 순서 변경이나 위젯 자체 이동이 아님을 확인한다.
3. **높이별 첫 화면:** 같은 폭에서 세 높이를 만들어 캡처하고 각 영역의 첫 화면 가시 항목 수를 표로 기록한다. 4×4 2단과 더 긴 크기, 좁고 긴 크기도 확인한다. 늘렸는데 빈 공간만 커지거나 프로젝트가 계속 1개면 실패다.
4. **상태 변화:** 스크롤한 뒤 새로고침·다른 todo 체크·undo·오류가 생길 때 해당/다른 목록의 접근과 위치가 안정적인지 확인한다. 큰 글씨·시스템 배율·0/50/100% 불투명도도 대표 조합으로 확인한다.
5. **색상:** 수집기의 실제 응답 형태를 반영한 통합 fixture를 사용하고, malformed/기본색/개별색/라벨색/같은색/색만변경을 검사한다. 가짜 upstream→원격 JSON→앱 저장→원형 마커를 연계 검증한다. 실제 계정은 별도 확인 상태로 남긴다.
6. **따뜻한 조합:** 같은 어두운 배경과 같은 일정을 유지한 채 신규 3종을 각각 실제 Glance로 캡처한다. 색상표 수치뿐 아니라 빨강/주황/노랑 계열임이 화면에서 확인되어야 하며 Google 점은 바뀌면 안 된다.
7. **기존 기능:** sha 총 4회 상한·unknown 필드·캐시·pending/undo·빠른 로컬 표시·프로젝트 checked 제외·사용자 순서·시간 경계 갱신을 퇴행시키지 않는다.

각 구현 단계 후 `android/gradlew.bat test assembleDebug`, 최종 `test assembleDebug lintDebug --console=plain`와 Apps Script Node 테스트를 실제 실행한다. unit planner의 숫자만 바꿔 스크롤 구현 완료로 처리하지 않는다. 익명 fixture는 에뮬레이터/격리된 테스트 데이터에 넣고 사용자 실기기의 기존 계정·캐시·토큰을 강제로 덮지 않는다. 장치가 없으면 에뮬레이터와 debug 전용 익명 harness를 사용하며, 제스처 검증 자체가 불가능하면 B/E의 검증 부분은 미완료로 명시한다.

## 8. 산출물·안전한 업데이트·인계

- `docs/android-scroll-colors-verification.md`: S1~S4별 구현/자동/실제 제스처/개인 Google 미확인 대응, 높이별 가시량 표, 마지막 항목 증거, 새 3팔레트, 색상 원인과 확인 단계.
- 익명 캡처 `docs/android-scroll-colors-screenshots/`. 실제 개인 제목/토큰/메일은 저장소나 로그에 남기지 않는다.
- `docs/google-calendar-setup.md`에 **현재 Code.gs와 manifest/Calendar API 활성화/diagnoseCalendarColors/refreshCalendarColors/원격 색 갱신/위젯 갱신**의 순서를 작성한다. 앱 APK 교체만으로 계정의 Apps Script가 업데이트되는 것처럼 설명하지 않는다.
- 기존 `applicationId`, debug 서명·Keystore·계정·위젯별 설정을 유지하고 versionCode를 올린다. uninstall/clear-data 금지. 출력은 기본 app-debug.apk와 `android/app/build/outputs/apk/debug/Dashboard-scroll-colors-debug.apk`, versionName/versionCode·SHA-256을 기록한다.
- `docs/android-setup.md`, `docs/work-plan.md`, `PLAN.md`를 실제 결과에 맞게 업데이트하고 대시보드에 기존 과제를 합친다. 초기 성공 기록을 삭제하거나 이번 성공으로 재사용하지 않는다.
- 개인 Apps Script 적용이 미완료면 색상이 '고쳐졌다'고 단정하지 않고 로컬 코드 수정·연계 fixture·실제 설치/색상 확인을 구분한다. 가능한 구현/검증/APK는 모두 끝내고 필요한 실제 사용자 동작만 남긴다.
