# 위젯 기능 맞추기 업무계획서 (웹앱 → 안드로이드 위젯)

작성일: 2026-11-07 (KST) · 계획·검수: Claude Opus 세션 · 실제 구현: 새 **Claude Sonnet / high** 세션 ([수행지시문 06](instructions/06-android-widget-parity-sonnet.md))

## 1. 배경

위젯은 2026-11-01(versionCode 6, 1.5)까지 꾸미기·2단 구성·영역별 스크롤·일정 색상을 끝낸 뒤 보류했다. 그 사이 웹앱(PWA)에 여러 기능이 붙었다(단계 6·7, PMR-Wiki 탭). 위젯은 `todos.json`을 **같이 쓰는** 프로그램이다. 그래서 웹앱이 새로 쓰는 필드를 위젯이 모르면 표시만 틀리는 것이 아니라 데이터가 어긋난다.

## 2. 현재 위젯 기능 (코드 확인 2026-11-07, `origin/main` 5c1008f)

| 영역 | 위젯에 있는 것 |
|---|---|
| 연결·동기화 | GitHub 토큰(Keystore 암호화), 30분 주기 + 새로고침 버튼, 파일별 캐시·부분 실패·오래된 캐시 표시 |
| 할 일 | 체크 즉시 반영(보류 오버레이), 저장 중 표시, 완료 실행 취소, 자정 초기화 |
| 오늘 일정 | `calendar.json` 오늘 일정, Google 개별 색 원형 점, 다음 일정, 시작·종료 시각 갱신 |
| 프로젝트 | active 프로젝트, 진행률, 사용자 확인(checked)을 뺀 다음 과제 |
| 화면 | 2×2·4×2·4×4 크기별 구성, 영역별 독립 스크롤, 위젯별 색상·글씨·투명도, 다크·따뜻한 조합 7종 |
| 관리 앱 | 연결 설정, 위젯별 꾸미기, 위젯 추가, 웹앱 열기, 도움말 |

## 3. 웹앱에만 있는 기능과 판정

### 3-1. 데이터 불일치 (버그, 반드시 고침)

`domain/TodoRules.kt`와 `GitHubRepo.updateTodo*`가 초기 형식(`daily`/`none`, `doneOn`만)에 머물러 있다. 웹앱 `web/rules.js`와 비교하면 다음과 같다.

| # | 웹앱 규칙 | 위젯 현재 동작 | 결과 |
|---|---|---|---|
| B1 | `weekly`는 `days`에 오늘 요일이 있을 때만 보임 | 요일과 관계없이 항상 보임 | 쉬는 요일에도 목록에 뜸 |
| B2 | 반복(`daily`·`weekly`)은 `doneOn == 오늘`이어야 완료 | `daily`만 반복으로 봄. `weekly`는 `doneOn != null`이면 완료 | 요일 반복 할 일이 한 번 체크하면 **영원히 완료**로 보임 |
| B3 | 한 번 할 일에 미래 `date`가 있으면 그날까지 숨기고 '예정 n개'로 표시 | 그대로 보임 | 내일로 미룬 일이 오늘 목록에 남음, 진행률 분모 틀림 |
| B4 | 반복 할 일을 체크하거나 취소하면 `history` 갱신, 취소하면 `doneOn`을 이전 완료일로 되돌림 | `doneOn`만 바꿈 | 위젯에서 체크한 날은 **연속 기록(🔥)이 끊김**, 취소 후 `doneOn`이 null이 되어 기록이 사라짐 |
| B5 | 저장할 때 최상위 `updatedAt` 갱신 | 갱신 여부를 확인해야 함 | 확인 후 맞춤 |

`gtask`·`gsync`·`time`·`days`·`date`·`history` 같은 모르는 필드를 지우지 않는지도 테스트로 고정한다. Apps Script의 Google 할 일 동기화가 `gsync`를 비교하기 때문이다.

### 3-2. 위젯으로 가져올 기능

| ID | 기능 | 웹앱 위치 | 위젯 형태 |
|---|---|---|---|
| A | 할 일 규칙 일치(B1–B5) | `rules.js` | 표시·진행률·체크·취소를 웹앱과 같게 |
| C | 할 일 정보 표시: 시작 시간, 🔥 연속 기록(2 이상), 'n일 지남', '예정 n개' | `render()` | 행 앞의 시간, 행 끝의 작은 배지, 할 일 패널 머리에 '예정 n' |
| D | 할 일 추가 + 날짜·시간 읽기("내일 오후 3시 병원") | `addTodo`·`parseTodoInput` | 할 일 패널 머리의 `+`(48dp) → 대화상자 Activity. 한 번·매일·평일·주말 선택, 읽은 날짜·시간 미리보기 |
| E | 할 일 메뉴: 이름·반복 요일·날짜·시간 수정, 내일로 미루기, 삭제(되돌리기) | `openTodoMenu` 등 | 할 일 **제목**을 누르면(체크 원은 그대로 체크) 같은 Activity의 편집 모드 |
| F | 오늘 일정 → Google 캘린더 앱 열기 | `gcalUrl` | 일정 패널 머리를 누르면 캘린더 앱의 오늘. 앱이 없으면 웹 주소 |
| G | 프로젝트 다음 과제 '사용자 확인' 체크 | `toggleNext` | 4×4 프로젝트 행의 '다음 ·'을 누르면 다음 과제 목록 대화상자(동그라미 체크) → `projects.checked` 기록 |
| H | PMR-Wiki 요약 | PMR 탭 | `data/pmr-wiki.json`을 함께 읽어, 결정 대기(`decisions.need`)나 실패 작업(`jobs[].state == error`)이 있을 때만 머리 줄에 작은 칩 표시(예: `PMR 결정 2`). 누르면 웹앱 `#pmr`. 파일이 없거나 0이면 아무것도 안 보임 |

### 3-3. 위젯에 넣지 않는 것 (웹앱에서만)

| 기능 | 이유 |
|---|---|
| 순서 끌어서 바꾸기 | 위젯의 세로 스와이프는 목록 스크롤로 쓴다(지시문 05). 끌기와 충돌한다 |
| 프로젝트 상태 변경·삭제, 붙여넣기 업데이트, 지난 완료 정리 | 드물게 쓰고, 확인 단계가 필요한 관리 작업 |
| PMR 결정 '추천대로'·'보류', 학습 후보 버튼 | 확인창과 되돌리기가 필요한 결정이다. 위젯은 알리기만 하고 웹앱으로 보낸다 |
| 앱 알림(Web Push)·알림 기록(종) | 웹앱 푸시가 이미 폰에 온다. 네이티브 알림을 또 만들면 같은 알림이 두 번 온다 |
| 당겨서 새로고침 | 위젯에는 새로고침 버튼이 있다 |

## 4. 설계 기준

### A·B: 규칙은 한 곳에서 정하고 두 언어가 같은 답을 내게

- `web/rules.js`가 기준이다. Kotlin `TodoRules`를 그 함수(`scheduledOn`, `isDone`, `isVisible`, `isUpcoming`, `isStale`, `streak`, `recordHistory`, `repeatLabel`, `fmtDay`)와 같게 고친다.
- **교차 검증 벡터**: `scripts/gen_rule_vectors.js`(Node)가 `rules.js`를 불러 날짜·요일·history 조합 사례와 `parseTodoInput` 입력 문장 사례의 기대값을 `android/app/src/test/resources/rule-vectors.json`으로 만든다. Kotlin 테스트가 이 파일을 읽어 같은 답인지 확인한다. 웹 규칙이 바뀌면 벡터를 다시 만들고 Kotlin 테스트가 깨지는 구조다. 기존 `scripts/test_rules.js`의 입력 문장 11개는 반드시 포함한다.
- 체크 쓰기는 '목표 doneOn 값'이 아니라 '**완료/취소 의도**'를 원격 최신 항목에 적용하는 방식으로 바꾼다. 웹앱 `toggleTodo`와 같은 계산(`recordHistory`, 이전 완료일 복원)을 sha 재시도 루프 안에서 한다. 실행 취소는 완료 직전의 `doneOn`·`history`를 기억해 되돌리되, 그 사이 다른 기기가 바꿨으면 지금처럼 충돌로 알린다.
- 보류 오버레이(즉시 반영)도 같은 규칙으로 계산해서, 저장 전후 화면이 달라지지 않게 한다.

### C: 표시

- 시간 있는 할 일은 제목 앞에 `15:00`. 🔥n은 2 이상일 때만. 지난 한 번 할 일은 `n일 지남`(경고색). 예정 개수는 할 일 패널 머리 오른쪽에 `예정 n`.
- 2×2·4×2에서는 공간이 없으면 배지를 생략한다. 시간과 제목을 우선한다.
- 큰 글씨·투명도·다크·따뜻한 조합 7종에서 배지가 읽혀야 한다(대비 4.5:1 목표).

### D·E·G: 입력이 필요한 것은 작은 Activity로

- Glance 위젯에는 글자 입력이 없다. `Theme.Material3...Dialog` 계열의 투명 대화상자 Activity 하나(`TodoQuickActivity` 등)로 추가·편집을, 다른 하나(또는 같은 Activity의 모드)로 프로젝트 다음 과제 체크를 처리한다. 런처 위에 떠서 저장하면 닫힌다.
- 저장은 기존 `DashboardSyncCoordinator.mutex`와 sha 재시도(최대 4회, 덮어쓰기 금지)를 쓴다. 네트워크 실패면 대화상자를 닫지 않고 입력을 유지한 채 오류와 '다시 시도'를 보인다. 입력을 잃지 않는 것이 기준이다(오프라인 대기열은 이번 범위가 아님).
- 저장 성공 직후 캐시를 새 문서로 갱신하고 위젯을 다시 그린다(30분을 기다리지 않음).
- 삭제는 확인창 대신 되돌리기: 대화상자가 닫힌 뒤 위젯의 기존 실행 취소 줄에 '삭제됨 · 되돌리기'를 보이고, 원래 자리(다음 항목 앞)에 다시 넣는다. 웹앱 `deleteTodo`와 같은 규칙.
- 새 할 일: `id` = `t_` + 시간 36진수 + 랜덤, 배열 맨 뒤에 추가, 한 번 할 일은 날짜가 없으면 오늘(웹앱 `addTodo`와 같음). `createdAt`은 ISO 8601 + 오프셋.
- 프로젝트 다음 과제 체크는 `projects.json`의 `checked`에 `{text, at}`를 넣고 빼는 것만 한다(웹앱 `toggleNext`). 다른 필드는 건드리지 않는다. 위젯이 `projects.json`을 쓰는 것은 처음이므로 sha 충돌 테스트를 따로 둔다.
- 터치 영역: 체크 원과 제목을 나눈다. 체크 원 48dp는 유지하고, 제목 터치는 스크롤과 구분되게 짧은 탭만 받는다. 스크롤 중 오작동이 없어야 한다(지시문 05 검수 기준 유지).

### F: 캘린더 앱

- `Intent(ACTION_VIEW, content://com.android.calendar/time/<오늘 0시 millis>)`를 먼저 쓰고, 처리할 앱이 없으면 웹앱 `gcalUrl`과 같은 웹 주소로 연다.

### H: PMR-Wiki 칩

- `DashboardFile`에 `PMR("data/pmr-wiki.json", "pmr")`를 더한다. 404는 '없음'으로 처리해 오류 표시를 내지 않는다(PMR을 안 쓰는 사람도 위젯이 정상이어야 함).
- 필드 정의는 `docs/data-format.md`의 `pmr-wiki.json` 절과 PR #7(`origin/pmr-decisions`)의 `decisions`·`alerts` 설명을 따른다. 읽기만 한다.
- 칩 문구: 결정 대기 n건이 있으면 `PMR 결정 n`, 실패·놓친 작업이 있으면 `PMR 실패 n`(경고색). 둘 다 있으면 실패를 먼저. 동기화가 하루 넘게 없으면(`generatedAt`) `PMR 끊김`. 누르면 `<웹앱 주소>#pmr`(웹앱은 `#pmr`에서 PMR 탭을 연다 — PR #7).

## 5. 검수 기준 (완료 판정)

1. 규칙 벡터 테스트: Node가 만든 벡터 전부를 Kotlin이 통과한다. 사례에는 쉬는 요일의 weekly, 오늘 끝낸 weekly, 미래·오늘·지난 date, 지난 완료, 연속 기록 끊김·건너뛰는 요일, history 없는 옛 항목, 입력 문장 11개 이상이 들어간다.
2. 쓰기 테스트(MockWebServer 또는 기존 가짜 저장소): 반복 할 일 체크·취소 후 `history`·`doneOn`이 웹앱 계산과 같다. 모르는 필드가 그대로 남는다. 409/422 재시도, 실행 취소 충돌, 추가·편집·미루기·삭제·삭제 되돌리기, `projects.checked` 넣기·빼기.
3. 에뮬레이터 실제 렌더: 디버그 seed로 익명 데이터(쉬는 요일 weekly, 예정, 지난, 🔥, 시간, PMR 결정·실패)를 넣고 2×2·4×2·4×4를 캡처한다. 추가 대화상자 → 저장 → 위젯 반영 흐름은 가짜 서버나 격리된 테스트 저장소로 확인한다. 영역별 스크롤·체크 오작동 없음은 다시 확인한다.
4. `./gradlew.bat test assembleDebug lintDebug --console=plain`, `node --test integrations/google-calendar/tests/Code.test.cjs`, `node scripts/test_rules.js`, `node scripts/test_apps_script.js`가 통과한다.
5. 업데이트 APK: applicationId·디버그 서명 유지, versionCode 7 / versionName 1.6, 지우지 않고 덮어 설치된다. `Dashboard-parity-debug.apk`와 SHA-256.
6. `docs/android-widget-parity-verification.md`에 위 표의 B1–B5·A·C–H 대응표, 명령 결과, 캡처, 확인하지 못한 것을 남긴다.

**금지**: 실제 `morn24/dashboard-data`에 테스트 쓰기, 사용자 폰·계정·토큰·캐시 덮어쓰기, 개인 데이터 커밋, push 강제·main 직접 커밋·PR 병합.

## 6. 일정과 순서

A·B(데이터 정합성) → C(표시) → F·H(읽기만 하는 기능) → D·E(입력 대화상자) → G(프로젝트 쓰기) → 통합 검증·APK·문서·PR. 앞 단계가 끝날 때마다 커밋한다. D·E·G가 막히면 A–C·F·H까지로 PR을 열고 남은 것을 표시한다(데이터 버그 수정이 먼저 배포되는 것이 중요).
