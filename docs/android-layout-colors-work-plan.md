# Android 위젯 2단 레이아웃·일정 색상 개선 업무계획서

작성일: 2026-11-01 (KST) · 구현·검증 기록: Codex 세션 · 상태: 코드 구현 후 연결된 Android 실기기 검증

## 실행 상태

- L1~L4의 승인된 구현 범위는 이번 저장소 작업에서 반영했다. 변경 파일과 자동·실기기 검증 증거는 [완료 검증 기록](android-layout-colors-verification.md)에 정리한다.
- 실제 UI는 사용자가 지정한 연결 디버깅 폰에서 검증한다. Galaxy S25 실사용 확인과 개인 Google 계정의 색상 일치는 별도 사용자 확인 항목으로 남긴다.
- 이전 03 개선판의 사용자 데이터, 위젯 상태, 서명 키를 보존하고 앱을 `versionCode 5`로 올린다. 실제 Samsung 렌더 검수에서 고정 크기 버킷과 panel modifier의 폭 강제가 발견되어 수정했다.

## 1. 승인 범위와 사전 검수

사용자는 개선 APK 사용 후 다음 네 가지를 요청했다. 아래 설계 기준은 구현과 검수에 그대로 사용한다.

| 요구 | 이번에 확정할 결과 |
|---|---|
| L1 크기별 구성이 비슷함 | 2×2는 단일 요약, 4×4는 **실제 좌우 2단 대시보드**. 4×2도 가로 공간을 활용 |
| L2 Google 일정별 색상 | Google에서 지정한 일정 색을 우선 수집해 기존 `color`에 저장하고 일정 앞 **원형 마커**로 표시 |
| L3 영역이 잘 구분되지 않음 | 할 일·오늘 일정·프로젝트를 서로 다른 은은한 배경의 패널로 구분. 제목을 크게 키우지 않음 |
| L4 어두운 색상 조합이 한 가지 | 어두운 바탕을 유지하면서 선택 가능한 **4개 이상의 강조색 조합** 제공 |

### 현재 코드·화면에서 확인한 사실

- `DashboardWidget.kt`의 루트는 모든 크기에서 같은 `LazyColumn`이다. 크기별 planner는 행 수만 달리한다. 기존 `docs/android-ux-screenshots/widget-2x2-light.png`와 `widget-4x4-light.png`도 직접 열어 4×4가 세로로만 늘어난 것을 확인했다.
- 대부분 같은 배경 위에 `SectionLabel`을 쌓으며 할 일·일정·프로젝트 패널이 없다. 화면을 구분하려고 제목만 더 크게 하는 방향은 이번 요청과 맞지 않는다.
- `EventLine`은 문자열만 출력한다. `CalendarEvent.color`와 JSON mapper에는 색상이 이미 있지만 사용하지 않는다.
- `integrations/google-calendar/Code.gs`는 `color: cal.getColor()`만 사용한다. 개별 일정에서 바꾼 색은 이 단계에서 누락된다.
- `AppearanceColorMode.DARK`는 하나이고 `baseAccent`도 고정이다. `primary/secondary/tertiary`도 같은 강조색을 사용한다. Compose 미리보기의 색상 함수도 별도로 있어 실제 위젯과 차이 날 여지가 있다.
- 직전 검증 기록은 JUnit 69개·test/assembleDebug/lint 성공과 Pixel 6a 화면 캡처다. 이는 이번 레이아웃/색상 수정의 검증을 대체하지 않는다. S25 전체 확인과 개인 Google 일정 색의 실제 일치는 아직 확인하지 않았다.

기존 03 개선 범위의 Flow 기반 즉시 반영·실행 취소·위젯별 꾸미기·상태 표시·시간 경계 갱신은 유지한다. 기존 계정·토큰·위젯·서명을 보존하고, 새 서비스나 WebView 통합은 추가하지 않는다. Apps Script 로컬 코드와 설정 안내의 수정은 일정별 색상 요구에 필요한 승인 범위다.

## 2. L1: 크기별 레이아웃과 2단 구성

### 4×4 기본 구조

```text
┌────────────────────────────────────────────┐
│ 날짜 · 최근 상태             새로고침 · 설정 │
│ 오늘 완료/전체 · 진행률 · 다음 시간 일정      │
├─────────────────────┬──────────────────────┤
│ 할 일 패널           │ 프로젝트 패널        │
│ 체크 항목 / 저장 중  │ 이름                 │
│ 실행 취소 / 더보기   │ 진행률               │
│                     │ 미확인 다음 과제     │
├─────────────────────┤                      │
│ 오늘 일정 패널       │ 여러 active 프로젝트 │
│ ● 시각 · 제목        │                      │
│ ● 종일 · 제목        │                      │
│ 더보기               │ 더보기               │
└─────────────────────┴──────────────────────┘
```

- 헤더·한 줄 상태·요약은 전체 폭, 본문은 `Row`로 **왼쪽 할 일/일정, 오른쪽 프로젝트**를 배치한다. 기본 열 비율은 약 52:48, 사이 간격은 8dp를 출발점으로 실제 렌더에서 조정한다.
- 왼쪽은 위 할 일, 아래 오늘 일정 패널이다. 일정이 있는 기본 100% 글씨의 첫 화면에 세 영역의 일부가 동시에 보여야 한다. 프로젝트를 맨 아래까지 스크롤해야 처음 보는 구조를 허용하지 않는다.
- 가용 높이에 따라 왼쪽 두 패널에 공간을 나누고 각 패널의 표시 개수/스크롤/더보기를 결정한다. 단순히 할 일 3개×48dp와 더보기부터 모두 배치해 오늘 일정 패널을 아래로 밀어내지 않는다. undo가 생겨도 프로젝트 열과 일정 구획을 통째로 없애지 않는다.
- 루트 전체를 단일 세로 `LazyColumn`으로 유지하면서 '2단 모드'라는 이름만 추가하지 않는다. 고정 헤더와 본문 Row 아래 각 목록을 배치해 불필요한 스크롤 중첩을 피한다. 여러 독립 Glance 목록이 해당 런처에서 작동하는지 실제 확인한다. 문제가 있으면 패널별 가시 행 수+더보기로 구현하고, 전체를 단일 열로 되돌리지 않는다.
- 기본 제공량 상한은 기존 할 일 3개/오늘 일정 5개/active 프로젝트 4개이며, 화면에 동시에 전부 보이는 수와 같지 않다. 숨겨진 수·전체 보기와 안정 id/원래 배열 순서는 유지한다.

### 작은·중간 크기

- **2×2:** 단일 열 요약. 오늘 진행과 다음 시간 일정을 우선하고 할 일은 가용 높이에 맞는 최소 표시/체크를 제공한다. 큰 위젯을 줄인 2열을 사용하지 않는다.
- **4×2:** 폭을 활용해 할 일 요약/체크와 일정 요약을 좌우로 배치한다. 프로젝트는 수·첫 과제 등 들어가는 요약을 제공하고 상세는 4×4/전체 보기로 연결한다. 48dp 액션을 지키면서 헤더·상태가 본문을 모두 밀어내지 않게 한다.
- Glance `SizeMode.Exact`로 런처가 제공한 실제 dp 크기에서 다시 그린다. 고정 크기 버킷이 실기기 4×4를 최소 크기로 떨어뜨리는 문제가 렌더 검수에서 확인됐다. `WidgetLayoutPlan`에 명시적 열 수·패널 배치·표시 예산을 포함해 2×2와 4×4가 구조적으로 다름을 테스트한다. 표기 셀 수가 실제 dp와 항상 같다고 가정하지 않는다.
- 4×4의 표준 글씨와 앱 150%까지는 2단을 기본 유지한다. 큰 시스템 글꼴에서는 각 열의 행 수를 줄이고 줄바꿈·스크롤·더보기로 대응한다. 폭이 물리적으로 좁은 2×4 같은 경우만 작은/세로 레이아웃으로 분류한다. 폰트를 임의로 줄이거나 시스템 배율을 무시하지 않는다.

## 3. L2: Google 색상의 수집부터 원형 마커까지

### 호환되는 출력

- `calendar.json`의 기존 **`color: "#RRGGBB"`** 필드에 최종 표시색을 넣는다. 새 필수 필드나 Android의 Google 로그인은 필요 없다. 기존 웹앱도 같은 color를 사용하므로 자동으로 호환되어야 한다.
- 우선순위는 **개별 일정의 유효한 지정색 → 캘린더 기본색 → 마지막에 안전한 기본색**이다. 제목에 '업무'가 들어가는지로 색을 추측하지 않는다.
- 일정 본문·종일/반복/다일 판단·id·순서·동기화 기간은 유지한다. Android는 calendar 파일을 읽기만 한다. 공유 데이터 형식을 변경하지 않는다.

### 수집 구현

- Apps Script의 `CalendarEvent.getColor()`는 HEX가 아니라 색상 ID 문자열을 반환한다. 이를 숫자나 CSS 색상으로 바로 저장하지 말고 Google의 event 팔레트에서 HEX로 해석한다.
- Google Calendar 공식 문서에는 기존 `colorId`뿐 아니라 `eventLabelId`와 캘린더별 `labelProperties.eventLabels[].backgroundColor`도 있다. **업무별로 설정한 사용자 색상/라벨을 11개 고정 팔레트에만 가두지 않는다.** 색상 읽기 어댑터를 분리한다.
- 권장 경로는 기존 CalendarApp으로 일정 본문을 수집하면서, Google Calendar REST 읽기 API로 색상 메타데이터를 보강하는 것이다. `UrlFetchApp` + `ScriptApp.getOAuthToken()`을 사용하면 이미 manifest에 있는 calendar.readonly/external_request 범위 내에서 구성할 수 있다. API 활성화 등 추가 환경 조치가 실제 필요한지 구현자가 확인해 안내한다. Android에 OAuth 토큰을 전달하지 않는다.
- 기존 팔레트는 `Colors.get`의 `event` 매핑을 실행당 한 번 읽고 캐시한다. 캘린더별 라벨 메타데이터도 캐시한다. 라벨이 있는 캘린더는 `eventLabelVersion=1`로 읽은 일정 메타데이터와 결합한다. 이 모드에서는 기존 colorId가 무시될 수 있으므로 legacy 경로와 명시적으로 분리한다.
- REST 메타데이터는 캘린더·기간 단위로 페이지를 끝까지 읽는다. 반복 일정은 occurrence 기준으로 전개하고 취소 일정·변경된 회차를 처리한다. 일정 하나마다 API를 호출하는 N+1 구조를 만들지 않는다.
- CalendarApp의 `getId()`는 iCalUID이고 REST event.id와 다르다. **calendar id + iCalUID + 실제 회차 시작 Instant(종일은 날짜)** 같은 키로 결합하며 제목으로 매칭하지 않는다. 기존 출력 id는 바꾸지 않는다. 시간대가 다른 종일·이동된 반복 회차를 별도 fixture로 확인한다.
- 라벨색을 해석할 수 있으면 그것을 사용하고, 그렇지 않으면 CalendarApp getColor/legacy palette, 그 다음 cal.getColor로 내려간다. 미지 ID·빈 색·잘못된 HEX·권한/쿼터 오류가 전체 일정 삭제·빈 파일 저장으로 이어지지 않게 한다. 마지막 정상 팔레트 캐시를 사용하고 메타데이터 실패를 진단 가능하게 기록한다. 개인 제목·토큰은 로그에 남기지 않는다.
- 팔레트/라벨을 영구 고정하지 않는다. 라벨은 짧은 TTL, 공통 팔레트는 더 긴 TTL로 재확인하고 사용자가 수동 실행하면 강제 갱신할 수 있게 한다. 색만 바뀌어도 events 비교에서 변경으로 인식해 GitHub를 갱신한다.
- Google Calendar에는 GET만 한다. 일정 색을 바꾸거나 라벨을 생성/삭제하는 API는 호출하지 않는다. 개인 계정에 설치된 스크립트 수정·재승인이 필요한 경우 코드를 먼저 완성하고, `docs/google-calendar-setup.md`에 기존 프로젝트의 Code.gs 교체·저장·수동 syncCalendar 실행·필요 시 읽기 권한 승인·색상 확인 순서를 적는다. 사용자의 설치를 확인하지 않은 상태에서 실서비스 색상 동기화 완료라고 쓰지 않는다.

### Android 표시

- 오늘 일정 행과 다음 일정 요약 모두 앞에 **지름 약 8dp 원형 점**을 둔다. 글꼴의 `●` 문자 크기에 의존하지 말고 Glance가 지원하는 벡터/shape/drawable로 일관된 원을 렌더한다. 텍스트와는 6dp 정도 간격을 둔다.
- 원형 마커의 RGB는 유효한 원격 color를 그대로 사용한다. 위젯 강조색/다크 팔레트로 재매핑하거나 모두 같은 색으로 덮지 않는다. 필요하면 외곽선/중립 받침을 추가하고 원래 중심색을 유지한다.
- 종료 일정은 글자·상태로 구분하고 색상의 의미를 바꾸지 않는다. 색만으로 상태나 업무 종류를 전달하지 않으며 제목·캘린더 이름·시각을 접근성 정보로 유지한다.
- 잘못된/없는 color는 안전한 중립 점으로 표시하고 앱이 크래시하지 않게 한다. 점은 장식으로 취급하거나 행 설명에 통합해 TalkBack이 불필요한 '점'을 반복하지 않게 한다.

## 4. L3: 영역별 배경과 작은 제목

- 공통 `SectionSurface`/표시 모델을 만들어 할 일·오늘 일정·프로젝트의 패널을 구성한다. 각 영역에 **서로 다른 은은한 tint**, 8~12dp 내부 여백, 약 8dp 구획 간격, 완만한 모서리를 준다.
- 예: 할 일은 민트 계열, 일정은 푸른 계열, 프로젝트는 라벤더 계열. 실제 조합은 선택된 테마 역할값에서 결정한다. 빛나는 원색 카드나 제목의 대형화로 구분하지 않는다.
- 섹션 제목은 본문과 비슷한 10~12sp 기반의 중간 굵기, 일관된 위치로 한다. 앱 글씨 배율은 같은 비율로 적용한다. 날짜·요약도 불필요하게 여러 줄을 점유하지 않도록 한다.
- 진행 막대·링크·포커스/액션은 각 영역의 역할 색상을 사용하되 오류색은 별도 의미를 유지한다. 배경색만 달라지고 텍스트가 읽히지 않는 구성을 허용하지 않는다.
- 기존 배경 불투명도 설정을 모든 배경 fill에 일관되게 적용한다. 글자·아이콘·캘린더 원형 마커 자체에는 전체 alpha를 적용하지 않는다. 불투명도 0%에서는 공간/얇은 구획선으로도 구분 가능하게 하며, 대비 보조 옵션을 선택했을 때만 그 옵션의 보조 표면을 사용한다.
- 달력 파일이 404면 비어 있는 일정 패널을 남기지 않고 할 일 공간을 확장한다. 단순 '오늘 일정 없음'과 미연결/오류 캐시는 구분한다. 빈 프로젝트 등은 의미 있는 짧은 상태로 표시한다.

## 5. L4: 다크 테마의 여러 색상 조합

### 배경 모드와 팔레트 분리

- `AppearanceColorMode`의 기존 저장값은 유지한다. 별도 `accentPaletteId` 같은 선택값을 추가해 어두운 바탕에서도 여러 역할 색 조합을 고를 수 있게 한다. 새 키/필드는 기본값을 제공하고 이전 DataStore 값을 migration 없이도 읽을 수 있어야 한다.
- 최소 네 조합을 제공한다. 아래 값은 디자인 출발점이며 구현 단계에서 대비 검증 후 같은 성격의 값으로 조정할 수 있다.

| 조합 | 할 일/주요 액션 | 일정 패널 역할 | 프로젝트 패널 역할 |
|---|---|---|---|
| 민트·블루·라벤더 (기존 다크 기본 계승) | `#91D5B3` | `#AFC8FF` | `#D5B7ED` |
| 스카이·앰버·퍼플 | `#8CCEFF` | `#F2CC8F` | `#B8B5FF` |
| 라벤더·민트·피치 | `#C8B8FF` | `#97DCC5` | `#F0B8A8` |
| 앰버·스카이·모브 | `#F4CF8E` | `#9BCFFF` | `#D5BAED` |

- 어두운 패널 배경은 바탕과 역할 색상을 약 8~14% 혼합하는 방식으로 만들어 구분은 되되 본문을 압도하지 않게 한다. 밝은 모드에서는 더 어두운 역할 전경/밝은 tint 배경을 계산한다. 숫자를 고정해 가독성이 확보됐다고 가정하지 않는다.
- 자동 모드는 기기 Material 색의 여러 container 역할을 기본으로 사용한다. 사용자 지정 HEX 배경/강조색도 보존한다. 팔레트 선택이 사용자의 HEX를 암묵적으로 삭제하지 않게 하고, 모드별 무엇이 적용되는지 UI에서 명확히 한다.
- 꾸미기 화면의 색상 조합은 **실제 3영역과 진행률·액션이 들어간 견본**으로 선택한다. 이름만 바꾸거나 색 점 하나만 바뀌는 UI로 끝내지 않는다. 어두운 바탕 선택 상태에서 조합을 바꿔도 밝은 바탕으로 전환하지 않는다.
- `ResolvedWidgetColors` 같은 공통 순수 역할 해석기를 만들어 Compose 미리보기·Glance·pin/picker 예시에서 공유한다. 캘린더 데이터 색상은 이 해석기와 독립적이다.
- 위젯별 적용/전체 적용/draft 취소/기본값 복원/재시작 동작을 유지한다. 새 팔레트 기본값은 기존 다크의 녹색 계열을 계승하며 기존 위젯을 초기화하지 않는다.

## 6. 구현 단계와 검수 게이트

각 단계 후 기존 빌드 명령을 실행한다. 최종은 `android/`에서 `gradlew.bat test assembleDebug lintDebug --console=plain`. 기존 테스트를 유지하고 렌더링 검증을 별도로 한다.

| 단계 | 구현 | 검수 근거 |
|---|---|---|
| A | 4×4 실제 2단·4×2 가로·2×2 요약, 패널·밀도 | planner 열 수/구획 테스트 + 실제 3크기 첫 화면 비교 |
| B | Apps Script 색상 해석·색상 변경 동기화 + Android 점 | ID/HEX/기본색/라벨/반복회차/페이지/오류 fixture + 원형 마커 실제 RGB |
| C | 역할별 배경·다크 팔레트·공통 미리보기·저장 호환 | 네 조합의 역할값 차이·상태 보존·대비 계산 + 다크 4종 실제 캡처 |
| D | 통합 검증·설치 안내·업데이트 APK | 기존 체크/undo/반응 퇴행 없음 + test/assemble/lint + 아래 수동/실제 렌더 표 |
| E | S25·개인 Google 일정 실제 색상 확인 | 사용자가 개선 APK/스크립트 적용 후 확인. 확인 전 미완료 |

### 반드시 실제 화면으로 확인할 항목

1. 동일한 익명 fixture로 2×2와 4×4를 캡처한다. **4×4에 세로 경계로 나뉜 좌우 두 콘텐츠 열이 있고 프로젝트가 오른쪽에 보이는지** 검수한다. 항목 수만 달라진 단일 목록이면 A 실패다.
2. 4×4 첫 화면에 할 일·오늘 일정·프로젝트의 구획과 내용 일부가 동시에 보인다. 정상/오류 한 줄/undo 표시 때도 프로젝트가 화면 아래로 밀려 사라지지 않는지 확인한다.
3. 일반·앱 150%·큰 시스템 글꼴의 대표 조합, 밝음/어두움, 0/50/100% 불투명도에서 패널과 체크/새로고침/undo의 터치 영역을 확인한다. 작은 글씨로 강제 해결하지 않는다.
4. 적어도 빨강·파랑·초록 일정과 캘린더 기본색 fallback을 같은 화면에 넣어 원형 점이 서로 다르고 테마를 바꿔도 중심 RGB가 유지됨을 확인한다. 다음 일정 요약에도 점이 있어야 한다.
5. 동일한 어두운 바탕에서 네 팔레트를 바꾼 실제 Glance 화면을 캡처한다. 배경 모드·투명도·글씨 크기는 유지되고 액션/진행/패널 조합이 달라야 한다. Compose 미리보기만으로 통과하지 않는다.
6. 원격 색 문자열/라벨/미지 필드는 fixture로 검증하고, Apps Script에 색상만 변경했을 때 쓰기 발생·변경 없으면 무쓰기 동작도 검증한다. Node의 built-in test/vm 등 가벼운 harness를 사용해 의존성을 불필요하게 늘리지 않는다.
7. 기존 Flow 활성 세션의 체크 반영, pending 행·실행 취소·오프라인 캐시·정렬·checked 제외·일정 경계 재렌더가 유지되는지 확인한다. 48dp 터치와 배경색 대비는 자동 수치/실제 bounds로 증명하고 눈대중만으로 완료하지 않는다.

### 업데이트와 결과물

- `applicationId`, 기존 서명·Keystore·토큰/캐시/위젯별 설정을 유지한다. 새 필드 기본값·미지 palette id fallback을 구현하고 versionCode는 현재보다 올린다. uninstall/clear-data 없이 업데이트한다.
- APK: 기본 `app-debug.apk`와 `android/app/build/outputs/apk/debug/Dashboard-layout-colors-debug.apk`. 실제 파일·versionCode/versionName·SHA-256을 기록한다.
- `docs/android-layout-colors-verification.md`: L1~L4 각각 구현 파일/자동 테스트/실제 캡처/사용자 미확인 표, 변경 전후 비교, 색상 수집 경로와 팔레트 선택 결과, 빌드·APK·Apps Script 적용 절차.
- 캡처는 익명 데이터로 `docs/android-layout-colors-screenshots/` 등에 저장하고 개인 일정·토큰은 포함하지 않는다. 03의 과거 성공 기록을 이번 성공처럼 재사용하지 않는다.
- `docs/android-setup.md`, `docs/google-calendar-setup.md`, `docs/work-plan.md`, `PLAN.md`를 결과에 맞게 보완한다. UI 코드·Apps Script·검증까지 가능한 범위를 끝내고 실제 계정 스크립트 설치/재승인만 필요하면 그 구체 동작을 사용자에게 남긴다.
- S25와 실제 Google 색상 일치는 사용자 확인 전에는 완료 처리하지 않는다. 전역 공유 형식 변경이 필요해지면 해당 변경을 멈추고 이유를 알리되, 현재 `color` 필드로 가능한 구현은 계속 진행한다.

## 7. 공식 확인 자료와 이번 계획의 검수

- [CalendarEvent.getColor](https://developers.google.com/apps-script/reference/calendar/calendar-event#getColor()): 색상 ID 반환과 CalendarApp id의 의미를 확인했다.
- [Colors.get](https://developers.google.com/workspace/calendar/api/v3/reference/colors/get): event 팔레트를 읽는 공식 경로.
- [Calendar labels](https://developers.google.com/workspace/calendar/api/guides/labels): 캘린더별 라벨 색과 eventLabelVersion 경로.
- [Event resource](https://developers.google.com/workspace/calendar/api/v3/reference/events): iCalUID/start/eventLabelId/colorId 필드.
- Android 레이아웃·Glance 상태·접근성 공식 스킬/지침은 [기존 검토서](android-ui-ux-review.md)의 자료를 이어 사용한다. 실제 지원 API는 구현 시 확인한다.

설계 단계에서 정한 '4×4 두 열', '일정별 원색 점', '은은한 패널 배경', '다크 상태 네 조합'은 [완료 검증 기록](android-layout-colors-verification.md)에서 코드·자동 테스트·실기기 캡처로 대응시킨다. Apps Script 적용 전용 계정 동의와 Galaxy S25 사용자 확인은 완료 주장에 포함하지 않는다.
