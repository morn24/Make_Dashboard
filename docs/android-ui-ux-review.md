# Android 위젯 UI/UX 검토

검토일: 2026-11-01 (KST)

## 범위와 방법

사용자는 초안 APK를 사용했고 크기에 따른 레이아웃 전환을 확인했다. 이번 검토는 이미 요청한 **색상·글씨 크기·배경 투명도 설정과 탭 반응 속도 개선 외의 항목**을 찾는 작업이다. 앱 코드는 변경하지 않았다.

사용 목적은 홈 화면에서 오늘 할 일과 다음 일정을 빠르게 확인하고, 실수 없이 체크하는 것이다. 작은 화면에서는 정보량보다 읽기·터치·행동 결과의 명확성을 우선한다.

다음 Android 공식 스킬을 찾아 읽고, 현재 코드와 대조하는 검토 기준으로 적용했다. 별도 전역 설치는 하지 않았다.

- [Glance canonical widget layouts](https://developer.android.com/agents/skills/system/glance-canonical-layouts/skill): 체크 목록·액션·보조 정보 구조. 연결된 공식 `ListItem.kt`도 확인했다. `CheckListLayout.kt` 원문은 도구에서 가져오지 못했으므로 세부 구현을 인용하지 않는다.
- [Glance state updates and memory](https://developer.android.com/agents/skills/system/glance-appwidget-updates-and-memory/skill): 화면 상태·액션 후 갱신·복구. 현재 앱은 bitmap 중심이 아니므로 이미지 메모리 관련 항목은 적용 대상에서 제외했다.
- [Android 위젯 품질 기준](https://developer.android.com/docs/quality-guidelines/widget-quality): 크기 변화, 미리보기, 콘텐츠 최신성, 잘림, 빈 상태.
- [Android 접근성 지침](https://developer.android.com/guide/topics/ui/accessibility/apps): 터치 영역·의미 전달·명도 대비.
- [Compose WindowInsets](https://developer.android.com/develop/ui/compose/system/insets): 설정 화면의 시스템 바·키보드 대응.

스킬의 샘플 복사·`SizeMode.Exact` 전환 절차는 샘플 레이아웃 구현용이다. 이번 검토에서 원 요구인 `SizeMode.Responsive`를 변경 대상으로 단정하지 않았다. 고급 효과나 새 라이브러리 도입보다 현재 기능의 사용성을 먼저 검토했다.

근거는 `widget/`, `ui/`, `domain/CalendarRules.kt`, `data/DashboardSyncEngine.kt`, Worker와 XML이다. `adb devices -l`에는 연결된 기기가 없었고 실행 중 에뮬레이터도 없었다. 기존 AVD 이름은 Pixel_6a로 확인했다. **S25 화면의 실제 잘림·터치 좌표·명도 대비·TalkBack 출력은 직접 측정하지 않았다.** 아래에서 코드로 확인한 사실과 기기 확인이 필요한 위험을 구분한다.

## 우선순위 기준

- **우선**: 실수 복구, 잘못된 정보 인지, 핵심 행동 실패에 영향을 줌.
- **다음**: 탐색·정보 이해·설정 과정을 쉽게 함.
- 코드 확인은 구현 사실을 의미하며, 사용자 기기에서 증상이 재현됐다는 뜻은 아니다.

## 1. 체크를 잘못했을 때 되돌릴 경로가 없다 — 우선 / 코드 확인

**근거:** `DashboardWidget.kt:163`, `:216`에서 완료 항목을 먼저 제외한다. `TodoToggleRow`에는 완료 취소 목표값을 만드는 코드가 있지만 완료된 행을 보여주는 목록이 없다. 낙관적 완료도 같은 필터를 통과하므로 행의 `…` 처리 중 표시까지 사라질 수 있다.

**영향:** 손가락이 빗나가면 웹앱으로 이동해 되돌려야 한다. 체크가 접수된 것인지, 저장 중인지도 알아보기 어렵다.

**권장:** 보류 중에는 해당 행을 완료/저장 중 상태로 유지하고 중복 탭을 막는다. 저장 뒤에는 최근 완료 1개와 명시적인 `실행 취소` 또는 `완료 보기` 경로를 제공한다. 위젯에 일반 앱의 Snackbar가 있다고 전제하지 않는다. 취소도 완료값 반전 대신 목표값으로 저장한다.

**검증:** 체크·저장 실패·오프라인·취소·새 체크가 이어져도 제목과 결과가 명확하고 다른 항목을 취소하지 않아야 한다.

## 2. 터치 영역과 스크린리더 의미가 부족하다 — 우선 / 코드 확인, 크기 실측 필요

**근거:** `DashboardWidget.kt:263`은 18sp 문자 새로고침에 6dp padding만 붙인다. `:343`의 체크 행은 위아래 padding이 1dp이고 최소 터치 크기가 없다. `↻`, `□`, `☑`, `…`에 동작·상태 의미를 명시하지 않았다.

**영향:** 인접 할 일을 잘못 누르거나 작은 새로고침을 놓치기 쉽다. TalkBack이 문자 기호를 읽더라도 '어느 할 일을 완료하는가'가 충분히 전달되지 않을 수 있다.

**권장:** 액션 영역을 최소 48×48dp 기준으로 설계한다. 공간이 부족하면 표시 행 수를 줄이거나 스크롤/더보기를 사용한다. 체크박스의 선택 상태와 `아침 운동, 미완료, 완료로 변경` 같은 의미를 Glance가 지원하는 컴포넌트·semantics로 제공한다. 새로고침은 이름 있는 아이콘 액션으로 만든다. [공식 기준](https://developer.android.com/guide/topics/ui/accessibility/apps)

**검증:** S25 실측과 TalkBack으로 액션·현재 상태·저장 중 상태를 확인한다. 터치 영역을 늘리기 위해 작은 글자를 더 압축하지 않는다.

## 3. 더 많은 항목이 있어도 보이지 않는다는 안내가 없다 — 우선 / 코드 확인

**근거:** `DashboardWidget.kt:163`, `:216`, `:217`, `:235`는 할 일 3개·프로젝트 4개·일정 5개로 자른다. 나머지 개수나 전체 목록으로 이동하는 명시적 액션은 없다.

**영향:** 표시된 항목이 전체라고 생각할 수 있다. 특히 한 줄로 잘린 제목·다음 과제의 원문을 위젯에서 확인하기 어렵다.

**권장:** `할 일 3/8 · 전체 보기`, `일정 +2개` 등 숨겨진 수를 표시한다. 전체 보기 버튼은 우선 기존 웹앱을 열어도 된다. 해당 구역으로 바로 이동하는 링크는 웹앱에 실제 경로/앵커가 있을 때만 사용한다. 스크롤 목록 도입 시 항목 id와 액션 상태를 안정적으로 유지한다.

**검증:** 한도를 1개 넘는 데이터, 긴 한글·이모지, 20개 이상의 데이터에서 누락 안내와 전체 접근을 확인한다.

## 4. 크기별 정보량을 실제 가용 높이에 맞춰 줄여야 한다 — 우선 / 코드 위험, 화면 확인 필요

**근거:** `DashboardWidget.kt:58`의 140×140 / 300×140 / 300×300dp 세 구간에 고정된 Column을 쓴다. 중간 크기에는 헤더·오류·요약·진행 표시·두 목록·프로젝트가 함께 들어간다. 큰 크기는 3개 할 일·5개 일정·4개 프로젝트를 배치하지만 스크롤은 없다.

**영향:** 오류 한 줄이 추가되거나 시스템 글꼴이 커지면 아래 영역이 잘릴 위험이 있다. 넓은 위젯과 세로로만 긴 위젯에 똑같은 밀도를 적용하기도 어렵다.

**권장:** 항상 유지할 정보는 날짜·오늘 진행·핵심 액션·다음 일정으로 정한다. 나머지는 높이에 따라 행 수/열 수를 조정하고 더보기로 보낸다. 글씨 크기를 줄이는 방식으로 해결하지 않는다. `Responsive`의 bucket과 실제 런처 가용 크기를 함께 확인한다. [위젯 품질 기준](https://developer.android.com/docs/quality-guidelines/widget-quality)

**검증:** 세 크기와 그 사이의 리사이즈, 시스템 글꼴 100/130/150/200%, 오류 유무, 일정/프로젝트 최대 수를 교차 확인한다. 큰 글꼴에서는 전체 표시량보다 핵심 액션과 원문 접근을 보장한다.

## 5. '최근 갱신'과 일부 실패를 구분해야 한다 — 우선 / 코드 확인

**근거:** `DashboardSyncEngine.kt:96`, `:178`은 파일별 성공 시각 중 가장 최근 값을 전체 갱신 시각으로 쓴다. `DashboardWidget.kt:259`는 날짜 없이 HH:mm만 보여주고, `:272`는 첫 오류만 작은 한 줄로 보여준다.

**영향:** 일정만 새로 받아도 오래된 할 일까지 최신인 것처럼 읽힐 수 있다. 어제 09:00 데이터도 오늘 09:00처럼 보이며, 오류가 잘리면 복구 방법을 알 수 없다.

**권장:** `방금 확인`, `어제 09:00 · 오프라인`, `할 일 갱신 실패 · 이전 내용`처럼 상태와 범위를 표시한다. 성공 기준을 가장 최근 파일 하나로 삼지 않는다. 위젯에는 짧은 오류·재시도/설정 액션을, 앱에는 파일별 마지막 성공·오류 상세를 제공한다.

**검증:** 파일 하나만 성공, 하루 지난 캐시, 401/403, 네트워크 없음에서 화면이 전체 성공으로 보이지 않아야 한다.

## 6. 일정 시작·종료 시점에 표시 의미가 늦게 바뀔 수 있다 — 우선 / 코드 확인, 실제 지연 측정 필요

**근거:** `DashboardWidget.kt:131`, `:159`, `:211`은 그릴 때의 시각으로 다음 일정·진행 중을 계산한다. `DashboardWorkScheduler.kt:70`의 정기 갱신은 30분이고 일정 시작·종료 경계를 위한 로컬 재렌더 예약은 없다.

**영향:** 아직 시작 전으로 그린 일정이 시작된 뒤에도 그대로 남거나, 끝난 일정을 다음 일정으로 계속 보여줄 수 있다. 이는 탭 반응 속도와 별개의 정보 최신성 문제다.

**권장:** 캐시만 사용하는 날짜·시간 표시 갱신을 네트워크 읽기와 분리한다. 다음 중요한 시작/종료 경계에 가능한 범위에서 로컬 재렌더를 요청하고, 화면에는 절대 시작 시각을 남긴다. 새로고침과 앱 재진입에서는 반드시 현재 시각으로 다시 판단한다. 절전 중 정확한 분 단위 실행을 약속하거나 exact alarm 권한을 기본 요구하지 않는다.

**검증:** 일정 시작 전→진행 중→종료, 오프라인·절전 중 복귀, 시간대 변경을 확인한다.

## 7. 중간 크기에서도 다음 시간 일정을 보장해야 한다 — 다음 / 코드 확인

**근거:** `MediumDashboard`는 `remainingToday(...).take(2)`를 사용한다. `CalendarRules`는 종일 먼저 정렬하고, 중간 레이아웃에는 작은 레이아웃의 별도 `nextTimed` 요약이 없다.

**영향:** 종일 일정 2개와 30분 뒤 회의가 있으면 중간 위젯에서 회의가 보이지 않는다. 작은 위젯보다 긴급한 시간 정보가 적어지는 역전이 생긴다.

**권장:** 크기와 관계없이 다음 시간 일정 1개를 우선 유지하고, 종일은 별도 작은 표기/개수로 보여준다. 큰 크기의 상세 목록은 공유 데이터의 종일 우선 정렬을 그대로 유지한다. 저장 배열이나 데이터 약속을 변경하지 않는다.

**검증:** 종일 2개 이상 + 진행 중/임박 시간 일정이 있을 때 작은·중간·큰 위젯 모두에서 핵심 일정에 접근 가능해야 한다.

## 8. 웹앱 열기·체크·설정의 이동 목적을 구분해야 한다 — 다음 / 코드 확인

**근거:** `DashboardWidget.kt:92`는 위젯 바탕 전체를 웹앱 열기로 지정한다. 연결 후 위젯에 설정 액션은 없고, 대부분의 제목/구역은 별도 목적지가 없다.

**영향:** 체크 행을 조금 벗어난 터치가 브라우저 열기로 이어질 수 있다. 꾸미기 설정을 추가해도 홈 화면에서 그 설정을 찾기 어렵다.

**권장:** 헤더에 `Dashboard 열기`와 `위젯 설정` 목적을 명시하고 체크 액션을 분리한다. 빈 곳 탭으로 웹앱 열기는 기존 요구이므로 유지하되, 행 주변 오터치 범위를 줄이고 동작을 예측 가능하게 한다. 각 위젯의 다른 구성을 허용할 경우 widget id별 설정 진입점을 설계한다.

**검증:** 체크·주변 여백·제목·새로고침·설정 버튼의 터치 결과가 일관적인지 기기에서 확인한다.

## 9. '없음'과 진행률을 더 분명하게 표현해야 한다 — 다음 / 코드 확인

**근거:** 빈 할 일/프로젝트는 `없음`, 할 일이 전혀 없으면 진행률은 0/0과 0%다. `ProgressText`와 `ProjectLine`은 `■□` 문자 반복으로 막대를 표현한다.

**영향:** 할 일을 모두 마친 것과 처음부터 없는 것이 같은 빈 목록처럼 보인다. 문자 막대는 글꼴에 따라 폭이 바뀌고 읽기 순서도 번잡해진다.

**권장:** `오늘 할 일을 모두 마쳤어요`, `등록된 할 일이 없어요 · 웹에서 추가`, `진행 중 프로젝트 없음`을 구분한다. 막대는 Glance의 진행 표시 컴포넌트를 사용하고 숫자/스크린리더 설명을 함께 제공한다. 프로젝트의 다음 과제는 진행률보다 충분한 읽기 공간을 확보한다.

**검증:** 처음 사용·전부 완료·프로젝트 전부 홀드·일정 없음·목록 로딩 실패를 서로 다른 상태로 확인한다.

## 10. 설정 화면은 연결 후의 일상 사용에 맞게 바꿔야 한다 — 다음 / 코드 확인

**근거:** `SettingsActivity.kt:89` 이후는 연결 입력란과 같은 강조의 연결·배터리 버튼으로 구성된다. 연결 완료 후에도 위젯 관리/웹앱 열기/최근 상태 요약이 없다. 위젯 추가는 안내 문장만 있고 picker 미리보기는 앱 아이콘이다(`dashboard_widget_info.xml:8`).

**영향:** 매번 앱을 열 때 재설정이 필요한 것처럼 보이고, 원하는 크기의 위젯이 어떻게 보일지 설치 전에 알기 어렵다.

**권장:** 기본 화면은 `연결 상태 / 위젯 관리 / 꾸미기 / 도움말`로 나누고 owner/repo/branch는 `연결 변경`에 모은다. 최초 연결 후 `위젯 추가`와 `웹앱 열기`를 제공하고 지원 런처에서는 pin 요청을 사용한다. 실패 시 수동 추가 안내로 돌아간다. 토큰 발급·권한 안내를 화면에서 접근 가능하게 하고, 실제 레이아웃을 반영한 preview를 제공한다. 배터리 안내는 보조 행동으로 둔다.

**검증:** 처음 연결·기존 연결 재진입·토큰 만료·위젯 미추가·이미 추가됨·pin 미지원에서 다음 행동이 명확해야 한다. 연결 확인은 읽기 권한만 검사하므로 '체크 저장 권한까지 검증됨'이라고 표현하지 않는다.

## 11. 설정 화면의 시스템 바와 화면 재생성 대응이 필요하다 — 우선 확인 / 코드 위험

**근거:** targetSdk는 36인데 `SettingsActivity.kt:83`은 `imePadding`과 고정 여백만 사용하고 system bar/safe drawing inset 처리가 없다. `styles.xml`은 밝은 상태 바 설정을 고정한다. `SettingsActivity.kt:52`는 Android ViewModel 대신 일반 객체를 매 onCreate에 만들고 activity lifecycleScope를 쓴다.

**영향:** 기기와 내비게이션 방식에 따라 상태 바/하단 영역과 겹칠 위험이 있다. 회전·다크 모드 전환 등 Activity 재생성 시 미저장 일반 입력과 진행 상태가 초기화될 수 있다.

**권장:** 시스템 바·cutout·키보드 inset을 함께 처리하고 현재 테마에 맞는 바 아이콘 대비를 확인한다. 비밀이 아닌 입력과 상태는 수명에 맞는 ViewModel/상태 저장으로 관리한다. **토큰 평문을 SavedState/디스크에 저장하는 방식으로 보완하지 않는다.** [공식 inset 설명](https://developer.android.com/develop/ui/compose/system/insets)

**검증:** Android 15/16, 제스처/3버튼 내비게이션, 키보드 표시·가로 화면·회전·연결 확인 중 재생성. 겹침 여부는 실제 렌더링 확인 전까지 미확인이다.
